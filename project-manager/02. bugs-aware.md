### BUG-012 — Form controls do painel com fonte Arial (≠ Inter) (CORRIGIDO 02/08/2026)
- **Local:** `restaurante/src/assets/main.css`
- **Descrição:** selects, abas e botões do painel renderizavam com `font-family: Arial` (UA stylesheet do navegador) porque o CSS global só definia a Inter no `body` — `button/input/select/textarea` não herdam fonte por padrão.

### BUG-018 — CEP fora do raio: fallback de coordenadas usava o CENTRO da cidade (ENCONTRADO/CORRIGIDO 08/08/2026)
- **Local:** `app/backend/src/services/cep.js` (buscarCEP) → afeta `frete.js` (`calcularFrete`/`validarEntrega`) e o endpoint `POST /pedidos/calcular-frete`
- **Descrição:** a BrasilAPI **não retorna coordenadas para a maioria dos CEPs** (ex.: 05340-040, 06172-200). Quando isso acontecia, o fallback usava as coordenadas do **CENTRO da cidade** (mapa CIDADE_COORDS). Para cidades grandes isso distorce o cálculo: um pedido para **Vila Lageado/SP (CEP 05340-040), que fica a ~4,4 km em linha reta do restaurante Palazzo (CEP 06172-200, Osasco)**, era calculado como **16,27 km** (centro de SP ↔ centro de Osasco) → estourava o maior raio cadastrado (10 km) → erro **"Desculpe, não entregamos na sua região."** (reportado pelo usuário como "fora do raio de atendimento").
- **Correção:** adicionada a **AwesomeAPI** (`https://cep.awesomeapi.com.br/json/{cep}` — gratuita, sem API key) como tentativa 1.5 do `buscarCEP`, retornando **coordenadas reais do CEP** (lat/lng) antes do fallback por cidade. Fluxo agora: BrasilAPI (com coords) → AwesomeAPI (coords reais) → fallback por cidade → ViaCEP.
- **Validação (produção):**
  - `buscarCEP('05340040')` → origem `awesomeapi`, lat -23.5549774, lng -46.7557409 ✅
  - `validarEntrega` → **DENTRO DO RAIO**: 4,41 km · faixa 5 km · frete **R$ 10,00** · tempo 25–45 min ✅ (antes: fora do raio)
  - Regressão: Osasco 06230-060 → 1,96 km · R$ 7,00 · 20–35 min ✅; CEPs distantes (01310-100 centro SP, 20040-020 RJ) continuam **fora do raio** ✅
  - Anti-adulteração de frete segue funcionando (valorFrete divergente é rejeitado) ✅
- **Calibração de raios (08/08/2026, mesmo bug):** com as coordenadas reais do CEP em mãos, confirmou-se que o Palazzo estava cadastrado **2,74 km** longe do endereço real (coords do centro de Osasco). Corrigido em produção:
  - `restaurantes` (id=1): latitude/longitude → **endereço real** (São Pedro, Osasco: -23.5451884, -46.8149413) — todos os cálculos de distância agora partem da origem correta.
  - `raios_entrega` (id=1) recalibrados considerando que a distância calculada é **em linha reta** (rota real ≈ 1,4× a linha reta, moto ~22 km/h, preparo 20 min): 1 km → 10-15 min · **R$ 6,00**; 3 km → 15-25 min · **R$ 8,00**; 5 km → 25-35 min · **R$ 10,00**; 10 km → 40-55 min · **R$ 15,00**.
  - Simulação pós-calibração: São Pedro 0,8 km/R$6 · Centro Osasco 3,9 km/R$10 · Vila Lageado 6,1 km/R$15 · Butantã 9,1 km/R$15 · Pinheiros rejeitado (fora) ✅
- **Status:** ✅ **CORRIGIDO no código + banco** — ⏳ falta o redeploy no Portainer para valer em produção.

### BUG-014 — Suspeita: bucket GLOBAL no rate limit de login via nginx (CORRIGIDO 16/08/2026)
- **Local:** infra (router/nginx) + `app/backend/src/middleware/rateLimiter.js` (`loginLimiter`)
- **Descrição:** probes simultâneos mostraram que o tráfego via domínio HTTPS (nginx) e o acesso direto à API (IP:8090) consomem **buckets diferentes** do `loginLimiter`. Causa raiz: em produção o tráfego da UI passa por **2 proxies** (NPM externo → router nginx → backend), mas o backend usava `app.set('trust proxy', 1)` — com 1 hop configurado, `req.ip` virava o IP do NPM para **todos** os clientes da UI → todos compartilhavam 1 bucket de 5 tentativas/15min (um usuário/atacante podia bloquear o login de todos).
- **Correção:** `app/backend/src/index.js` — `trust proxy` agora é uma **função que confia apenas em IPs privados** (rede Docker: 10./172.16-31./192.168. + loopback). Isso resolve o IP real com múltiplos proxies e **não aceita spoofing**: um cliente que acessa direto pela porta pública 8090 tem remoteAddress público (não confiável) → `X-Forwarded-For` forjado é ignorado.
- **Validação:** simulação com Express — cliente público via 2 proxies (NPM+router) → `req.ip` = IP real do cliente ✅; 3 proxies ✅; acesso direto → IP da conexão ✅; XFF forjado por cliente não-confiável ignorado ✅. Backend sobe e health 200 ✅. O `loginLimiter`/`apiLimiter`/etc. usam `req.ip` como chave padrão do express-rate-limit, então a correção vale para todos.
- **Status:** ✅ **CORRIGIDO no código** — ⏳ falta commit/push/redeploy (Portainer) para valer em produção.

### BUG-016 — RLS inefetivo: app conecta como SUPERUSER no Postgres (ENCONTRADO 03/08/2026)
- **Local:** banco de produção — role `default` tem `rolsuper=t, rolbypassrls=t`; todo o acesso do backend usa essa role.
- **Descrição:** as policies de RLS (clientes, pedidos, produtos, imagens, ...) existem mas são **bypassadas** porque o Postgres ignora RLS para superusers. O isolamento multi-tenant dependia só das cláusulas `WHERE restaurant_id = $1` no código.
- **Correção (migration 029, aplicada 03/08/2026):**
  - Role **`app_user`** (LOGIN, NOSUPERUSER, NOBYPASSRLS) criada + GRANTs (schema, tabelas, sequences, default privileges). O runtime do backend passa a usar `DB_USER=app_user` (no próximo deploy; stack.env + override DB_PASS no Portainer).
  - **WITH CHECK adicionado a TODAS as policies de isolamento** (10 tabelas) — sem WITH CHECK, INSERT/UPDATE de role não-superuser eram negados pelo RLS.
  - **RLS habilitado nas 4 tabelas sem isolamento**: `banners`, `categorias`, `pagamentos`, `raios_entrega` (policy de tenant com WITH CHECK).
  - **Jobs cross-tenant corrigidos**: `pollingRede` itera por tenant (`queryForTenant`/`transactionForTenant` em `database.js`); `redeWebhookHandler.processarEventoRede(payload, tenantId)` recebe o tenant explícito (webhook/polling não têm request).
  - `migrate.js`/seeds/scripts usam `DB_ADMIN_USER/PASS` (DDL); placeholder `__APP_DB_PASSWORD__` é substituído por `DB_PASS` em tempo de aplicação (re-run safe: senha só é (re)definida se ainda não existir; migrate.js pula a 029 sem DB_PASS).
  - **Validação (produção):** INSERT cross-tenant em `produtos`/`pagamentos` → `ERROR: new row violates row-level security policy` ✅; SELECT/UPDATE/DELETE isolados ✅; login admin e cliente + rotas protegidas em smoke test com container descartável como `app_user` ✅; produção intacta (ainda roda como superuser até o redeploy).
- **⚠️ Riscos residuais (aceitos e documentados):**
  - `restaurantes`, `refresh_tokens` (legada), `webhook_events` **sem RLS** — fluxos cross-tenant por design (tenantResolver por domínio, dedup de webhook). `restaurantes` contém credenciais Rede por tenant — leitura cross-tenant por `app_user` é possível (como era antes); mitigação futura: coluna-level grants ou rotação + segregação.
  - **Role-based policies não restringem**: as policies de isolamento são PERMISSIVE (OR) — o RLS agora garante **isolamento por tenant** no banco; a separação por cargo/role continua no middleware da aplicação. Ex.: um cliente logado consegue SELECT de todos os pedidos do seu tenant via a policy de isolamento (mas a API filtra por `cliente_id`).
  - Superuser `default` **continua existindo** (usado por migrations/seeds via `DB_ADMIN_USER/PASS`). **Recomendado:** rotacionar a senha do `default` (`ALTER ROLE default PASSWORD ...`) e manter o novo valor SÓ no override do Portainer (repo é PÚBLICO).
- **Status:** ✅ **CORRIGIDO no banco + código** (aplicado em produção) — ⏳ **ativar em runtime** no próximo deploy (backend passa a conectar como `app_user`).

### BUG-017 — Tempo de preparo/previsão exibidos com +3h (timestamps naive UTC interpretados como fuso local) (ENCONTRADO/CORRIGIDO 08/08/2026)
- **Local:** `app/backend/src/config/database.js` (parser do driver pg) + banco — `pedidos.criado_em/aceito_em/pronto_em/...` e `pagamentos.*` são `timestamp without time zone` gravados em UTC (sessão Etc/UTC, `NOW()`).
- **Descrição:** o `node-postgres` interpreta `timestamp without time zone` como hora **local** do processo Node. Com o container em `TZ=America/Sao_Paulo` (docker-compose) ou máquina local BR, toda data saía **+3h deslocada**: o pedido #1189 (criado 22:15Z = 19:15 BRT) era enviado pela API como `2026-08-09T01:15:07Z`. No frontend (KDS/Orders "Tempo", TrackingView countdown/previsão, timer PIX) o pedido parecia 3h no futuro → countdown de **"~225 minutos"** e previsão errada em pedidos recém-criados (sintoma reportado: "tempo de preparo do pedido 1189 muito acima do comum"). Também estendia em 3h a expiração do PIX no `pollingRede` (comparação `new Date(criado_em)` vs `Date.now()`).
- **Correção:**
  - `pg.types.setTypeParser(pg.types.builtins.TIMESTAMP, ...)` em `config/database.js` trata o valor armazenado como UTC (anexa 'Z') → a API envia o instante correto independente do fuso do processo. Validado: #1189 agora é enviado como `2026-08-08T22:15:07.544Z`.
  - `redeWebhookHandler.js`: `pago_em` passou a ser gravado com `NOW()` do banco (antes `new Date()` gravava hora local, desalinhando do resto).
  - ⚠️ **Dados históricos:** `pago_em` de PIX processados ANTES deste fix ficaram gravados em hora local — com o parser UTC, passam a ser lidos 3h antes (somente exibição; sem impacto em fluxos).
  - ✅ **Backfill (08/08/2026):** `UPDATE pagamentos SET pago_em = pago_em + interval '3 hours' WHERE pago_em < criado_em` executado em produção → **0 linhas afetadas** (a tabela `pagamentos` está vazia — nenhum pagamento online processado ainda; Rede aguardando credenciais reais). Nada a corrigir por enquanto.
- **Correção definitiva (migration 035, aplicada 08/08/2026):** todas as 38 colunas `timestamp without time zone` (24 tabelas) foram convertidas para `timestamptz` com `USING col AT TIME ZONE 'UTC'` (interpretação explícita dos valores existentes como UTC) + `ALTER DATABASE delivery SET timezone TO 'UTC'` (hardening das comparações com date-string/CURRENT_DATE). A migration é idempotente (o migrate.js roda todas a cada deploy). Com `timestamptz`, o driver pg lê e grava o instante absoluto em qualquer fuso — validado: leitura de `#1189` nativa = `2026-08-08T22:15:07.544Z` ✅ e escrita com `new Date()` num campo timestamptz preserva o instante ✅. O parser customizado em `config/database.js` ficou como defesa em profundidade para eventuais colunas naive futuras.
- **Status:** ✅ **CORRIGIDO** — código (parser + `pago_em = NOW()`) e banco (migration 035 aplicada em produção). ⏳ Falta apenas o redeploy no Portainer para o código novo entrar em produção (o banco já está correto).

### BUG-019 — "Dados inválidos" ao confirmar pedido: coordenadas do CEP chegavam como STRING (ENCONTRADO/CORRIGIDO 08/08/2026)
- **Local:** `app/backend/src/services/cep.js` (caminho AwesomeAPI, do BUG-018) → quebrava o Zod de `POST /pedidos` e `POST /pagamentos/criar` ("Dados inválidos." / `VALIDATION_ERROR`)
- **Descrição:** regressão introduzida pelo BUG-018: o caminho AwesomeAPI retornava `latitude: String(data.lat)` / `longitude: String(data.lng)` — **strings** — enquanto TODOS os outros caminhos do `buscarCEP` (BrasilAPI, fallback por cidade, ViaCEP) retornam **numbers**. O schema de criação de pedido (`createOrderSchema`, `latitude_cliente: z.number()`) e o de pagamento online (`pedido.latitude: z.number()`) rejeitavam a string → **"Dados inválidos."** ao confirmar o pedido. Como o AwesomeAPI é o caminho usado justamente pelos CEPs sem coords na BrasilAPI (ex.: 05340-040), o erro era **intermitente por CEP** — pedidos de CEPs com coords na BrasilAPI continuavam passando.
- **Correção (3 camadas):**
  1. `cep.js` — AwesomeAPI agora retorna `Number(data.lat)` / `Number(data.lng)` (consistente com os demais caminhos).
  2. `CheckoutPanel.vue` — `Number(form.latitude)`/`Number(form.longitude)` nos payloads de pedido (COD) e pagamento online (defensivo).
  3. Schemas (`pedidos/index.js` + `pagamentos/index.js`) — `latitude`/`longitude` usam `z.preprocess` que aceita string|number e trata `null`/vazio/**whitespace**/`NaN` como ausente (evita coords `0,0`, que distorceriam o raio; `Number('   ') === 0` em JS — guard com `String(v).trim()`).
- **Validação:** `buscarCEP('05340040')` → origem `awesomeapi`, `latitude: -23.5549774` (**typeof number**) ✅; payload com string aceito e normalizado ✅; payload com number/null/vazio/whitespace/NaN/zero — 10/10 casos passam ✅; `node --check` nos 3 arquivos ✅.
- **Status:** ✅ **CORRIGIDO no código** — ⏳ precisa commit + push + redeploy no Portainer para valer em produção.
