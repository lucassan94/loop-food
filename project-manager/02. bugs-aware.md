# 02. Bugs detectados — Projeto: Migração Asaas → API da Rede

> Última atualização: 02/08/2026 — Bugs BUG-001 a BUG-009, BUG-011 e BUG-012 foram **resolvidos/prevenidos**. Abaixo somente o que está **aberto**.

## 🐞 Bugs abertos

### BUG-012 — Form controls do painel com fonte Arial (≠ Inter) (CORRIGIDO 02/08/2026)
- **Local:** `restaurante/src/assets/main.css`
- **Descrição:** selects, abas e botões do painel renderizavam com `font-family: Arial` (UA stylesheet do navegador) porque o CSS global só definia a Inter no `body` — `button/input/select/textarea` não herdam fonte por padrão.
- **Correção:** reset global `button, input, select, textarea { font-family: inherit; }` após o bloco `body`. Os inputs de cor em ConfigView mantêm `monospace` (inline style tem precedência).
- **Status:** ✅ **CORRIGIDO** (build do restaurante OK).

### BUG-011 — Imagens do cardápio não apareciam (URLs sem tenantId) (CORRIGIDO 02/08/2026)
- **Local:** `produtos.imagem_url` (banco) + `backend/uploads/cardapio/` (disco)
- **Descrição:** após a migração multi-tenant, 44 produtos ficaram com `imagem_url` no formato antigo `/uploads/cardapio/13_....jpg` (sem tenantId) e arquivos em `uploads/cardapio/` (sem subpasta do tenant). A rota `serveUploadFile` exige `/uploads/{tenantId}/cardapio/{filename}` → 404 → fallback Unsplash.
- **Correção:** novo script `backend/src/corrigir-imagens-cardapio.js` (idempotente) move os arquivos para `uploads/{tenantId}/cardapio/` e atualiza `imagem_url` no banco. **44/44 migrados**, URLs novas servidas com **200** (validação por HTTP).
- **Status:** ✅ **CORRIGIDO no banco + disco local** — 37 arquivos órfãos (duplicatas não referenciadas) removidos de `backend/uploads/cardapio/` após verificação no banco (0 referências em produtos/banners). ⚠️ Em produção (Docker/volume `backend_uploads`) o mesmo script precisa ser executado dentro do container.

### BUG-010 — Tenant 3 (Loop) sem usuários após seeds
- **Local:** banco de produção — `restaurantes` id=3 (Loop)
- **Descrição:** os seeds (`seed.js`/`seed-tenant2.js`) só criam usuários nos tenants 1 (Palazzo) e 2 (SaborExpress). Após a limpeza, o tenant 3 ficou sem `restaurante_users`/clientes/entregadores.
- **Status:** ⏳ **PENDENTE** — criar acesso via módulo god (novo admin no tenant 3) se o tenant ainda estiver em uso.

### BUG-013 — App do entregador não exibe pedidos cancelados nem o motivo (ENCONTRADO 03/08/2026)
- **Local:** `app/entregador/src/App.vue` — `loadData()`
- **Descrição:** o app do entregador só busca `GET /pedidos?status=pronto_entrega`, `em_transito,cheguei_destino` e concluídos (`entregue`). Pedidos **cancelados** nunca são carregados nem exibidos, então o entregador não vê o motivo do cancelamento. O backend **salva o motivo** corretamente (`motivo_cancelamento` no pedido — confirmado via API), mas a UI não o consome.
- **Impacto:** EN-15 do doc de testes não é atendido pela UI; entregador fica sem contexto de cancelamentos.
- **Sugestão:** incluir `cancelado` na query de concluídos (com badge de motivo) ou criar uma aba/tela de cancelados.
- **Status:** ⏳ **ABERTO** (apenas documentado — testes verificam o motivo via API).

### BUG-014 — Suspeita: bucket GLOBAL no rate limit de login via nginx (ENCONTRADO 03/08/2026)
- **Local:** infra (router/nginx) + `app/backend/src/middleware/rateLimiter.js` (`loginLimiter`)
- **Descrição:** probes simultâneos mostraram que o tráfego via domínio HTTPS (nginx) e o acesso direto à API (IP:8090) consomem **buckets diferentes** do `loginLimiter` (o direto retornou 401 com `RateLimit-Remaining: 0` enquanto o HTTPS retornava 429 no mesmo instante). Se o nginx não propaga `X-Forwarded-For` (ou o `trust proxy` do backend não lê corretamente), `req.ip` = IP do container do nginx → **todos os clientes UI compartilham 1 bucket de 5 tentativas/15min** (um usuário pode bloquear o login de todos).
- **Status:** 🔍 **A INVESTIGAR** — conferir `proxy_set_header X-Forwarded-For` no router/nginx e o `app.set('trust proxy', 1)` do backend.

### BUG-015 — Push notifications quebrados em produção: VAPID ausente no .env (ENCONTRADO 03/08/2026)
- **Local:** deploy — `.env` do servidor não tem `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` (o `deploy.py env` não os gera); `app/backend/src/services/push.js` avisa `[Push] ⚠️ VAPID ... não configurados` e não envia notificação.
- **Correção:** o `stack.env` commitado na raiz (fluxo GitHub → Portainer) inclui as chaves VAPID (iguais às do `others/stack.env`) via `env_file` — o push volta a funcionar no próximo deploy pelo Portainer. No fallback SSH, adicionar VAPID_* ao `.env` do servidor.
- **Status:** ✅ **CORRIGIDO no repo** (stack.env) — ⏳ aplicar via redeploy Portainer.

### BUG-016 — RLS inefetivo: app conecta como SUPERUSER no Postgres (ENCONTRADO 03/08/2026)
- **Local:** banco de produção — role `default` tem `rolsuper=t, rolbypassrls=t`; todo o acesso do backend usa essa role.
- **Descrição:** as policies de RLS (clientes, pedidos, produtos, imagens, ...) existem mas são **bypassadas** porque o Postgres ignora RLS para superusers. O isolamento multi-tenant dependia só das cláusulas `WHERE restaurant_id = $1` no código.
- **Correção (migration 029, aplicada 03/08/2026):**
  - Role **`app_user`** (LOGIN, NOSUPERUSER, NOBYPASSRLS) criada + GRANTs (schema, tabelas, sequences, default privileges). O runtime do backend passa a usar `DB_USER=app_user` (no próximo deploy; stack.env + override DB_PASS no Portainer).
  - **WITH CHECK adicionado a TODAS as policies de isolamento** (10 tabelas) — sem WITH CHECK, INSERT/UPDATE de role não-superuser eram negados pelo RLS.
  - **RLS habilitado nas 4 tabelas sem isolamento**: `banners`, `categorias`, `pagamentos`, `raios_entrega` (policy de tenant com WITH CHECK).
  - **Jobs cross-tenant corrigidos**: `pollingRede` itera por tenant (`queryForTenant`/`transactionForTenant` em `database.js`); `redeWebhookHandler.processarEventoRede(payload, tenantId)` recebe o tenant explícito (webhook/polling não têm request).
  - `migrate.js`/seeds/scripts usam `DB_ADMIN_USER/PASS` (DDL); placeholder `__APP_DB_PASSWORD__` é substituído por `DB_PASS` em tempo de aplicação (re-run safe: senha só é (re)definida se ainda não existir; migrate.js pula a 029 sem DB_PASS).
  - **Validação (produção):** INSERT cross-tenant em `produtos`/`pagamentos` → `ERROR: new row violates row-level security policy` ✅; SELECT/UPDATE/DELETE isolados ✅; login admin e cliente + rotas protegidas em smoke test com container descartável como `app_user` ✅; produção intacta (ainda roda como superuser até o redeploy).
- **⚠️ Riscos residuais (aceitos e documentados):**
  - `restaurantes`, `refresh_tokens` (legada), `webhook_events` **sem RLS** — fluxos cross-tenant por design (tenantResolver por domínio, dedup de webhook). `restaurantes` contém credenciais Rede por tenant — leitura cross-tenant por `app_user` é possível (como era antes); mitigação futura: coluna-level grants ou rotação + segregação.
  - **Role-based policies não restringem**: as policies de isolamento são PERMISSIVE (OR) — o RLS agora garante **isolamento por tenant** no banco; a separação por cargo/role continua no middleware da aplicação. Ex.: um cliente logado consegue SELECT de todos os pedidos do seu tenant via a policy de isolamento (mas a API filtra por `cliente_id`).
  - Superuser `default` **continua existindo** (usado por migrations/seeds via `DB_ADMIN_USER/PASS`). **Recomendado:** rotacionar a senha do `default` (`ALTER ROLE default PASSWORD ...`) e manter o novo valor SÓ no override do Portainer (repo é PÚBLICO).
- **Status:** ✅ **CORRIGIDO no banco + código** (aplicado em produção) — ⏳ **ativar em runtime** no próximo deploy (backend passa a conectar como `app_user`).
