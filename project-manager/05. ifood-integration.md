# 05. Integração iFood — Plano de Implementação

> **Status:** Fases 1–4 e 6 implementadas · **Última atualização:** 08/08/2026
> Escopo aprovado: **Catálogo + Pedidos**, **entrega própria** (frota Kardapio Digital),
> **multitenant** (por restaurante, ativável na configuração do Admin).

---

## 1. Visão geral

A plataforma passa a operar pedidos do **iFood** lado a lado com os canais próprios
(delivery do app, salão/PDV, retirada). Cada restaurante (tenant) pode **ativar ou
desativar** a integração iFood na configuração do Admin, independentemente dos demais.

Modelo operacional:
- **Catálogo:** o cardápio do painel (categorias/produtos/preços/disponibilidade)
  é sincronizado **push** para o iFood (via API de catálogo).
- **Pedidos:** novos pedidos iFood entram na **fila/KDS** como pedidos internos
  com `origem = 'ifood'`, sem mudar o fluxo de cozinha que já existe.
- **Entrega própria:** o restaurante despacha com o **entregador da própria plataforma**
  (fluxo `dispatch` com modo entrega da loja) — sem depender do entregador do iFood.
- **Status:** cada mudança interna (aceitar, pronto, despachado, entregue, cancelar)
  é refletida de volta para o iFood via API.

### Restrições de negócio (multitenant)
- As credenciais de **parceiro de software (ISV)** são globais da plataforma (env).
- Cada tenant tem seu `merchantId` + flag `ativo` + ambiente (sandbox/produção).
- A integração **não pode afetar** tenants sem iFood (nenhuma chamada feita se inativo).

## 2. Como funciona a API do iFood (resumo técnico validado)

> Fonte: docs oficiais developer.ifood.com.br. URLs de base podem variar entre
> ambientes (`merchant-api.ifood.com.br` / `pos-api.ifood.com.br`) — confirmar na
> homologação.

### 2.1 Autenticação — OAuth 2.0 client_credentials
- `POST /authentication/v1.0/oauth/token` com `grantType=client_credentials`,
  `clientId`, `clientSecret` → `access_token` (validade ~6h, campo `expires_in`).
- Token **global do ISV**: não é por restaurante; o `merchantId` escopado nas requests.
- Necessário **cache + renovação automática** antes de expirar.

### 2.2 Recebimento de eventos — **POLLING** (modelo primário oficial)
- `GET /order/v1.0/events:polling?types=...` → lista de eventos
  (`id`, `code`, `createdAt`, `metadata.orderId`).
- `DELETE /order/v1.0/events/acknowledgment` (ou POST) com `[{ "id": ... }]`
  confirma o processamento e remove da fila.
- Polling **contínuo** (ex.: a cada 2–5s) enquanto houver pedidos ativos.
- Modelo mais robusto que webhook (controle da fila e retries).

### 2.3 Gestão do pedido (base `/order/v1.0/orders/{orderId}/`)
| Endpoint | Uso |
|---|---|
| `POST /acknowledgment` | Tomar ciência do pedido (evita timeout de SLA) |
| `POST /confirmation` | Aceitar o pedido |
| `POST /rejection` | Recusar (com `reason`) |
| `POST /readyToPickup` | Pronto para retirada |
| `POST /dispatch` | Despachar (entrega própria: informar modo/veículo) |
| `POST /delivery` / `POST /conclusion` | Entregue / concluído |
| `POST /cancellation` | Cancelar (com motivo) |

### 2.4 Eventos (máquina de estados)
- `PLACED` → `CONFIRMED` (loja) → `READY_TO_PICKUP` (loja) → `DISPATCHED` (loja)
  → `DELIVERED` (entregador) → `CONCLUDED` (iFood).
- `REJECTED` / `CANCELLED` (qualquer parte, com motivo), `INTEGRATION_ERROR`,
  `INVALID` (iFood — payload inválido).
- **SLA:** aceitar/rejeitar um `PLACED` em **~5–7 min**, senão o iFood pode gerar
  alerta de atraso ou cancelar automaticamente.

### 2.5 Payload do pedido (`GET /orders/{orderId}`)
`orderId` (id iFood), `displayId` (número exibido ao cliente), `items[]` (name,
quantity, unitPrice), `total`, `customer` (name, phone), `deliveryAddress`
(formattedAddress, coordinates), `payments[]` (methods), `merchantId`,
`salesChannel`, `orderTiming` (INSTANT/SCHEDULED).

### 2.6 Catálogo
- `PUT /merchant/v1.0/merchants/{merchantId}/catalogs` — sync de cardápio.
- Disponibilidade/preço: updates pontuais (esgotado/ativo) em tempo real.
- Changelog recente: campo `quantity` depreciado no ProductDTO (25/05/2026) e
  `itemGeneralTags` (06/04/2026) — **validar versões na homologação**.

### 4.2 Migração — `migrations/036_ifood.sql`
```sql
-- Configuração por tenant
CREATE TABLE IF NOT EXISTS ifood_settings (
  restaurant_id  INTEGER PRIMARY KEY REFERENCES restaurantes(id) ON DELETE CASCADE,
  ativo          BOOLEAN NOT NULL DEFAULT false,
  ambiente       VARCHAR(10) NOT NULL DEFAULT 'sandbox',  -- sandbox | producao
  merchant_id    VARCHAR(50),
  delivery_mode  VARCHAR(20) NOT NULL DEFAULT 'own',      -- own (entrega própria) | ifood
  sync_catalogo  BOOLEAN NOT NULL DEFAULT false,

  criado_em      TIMESTAMPTZ NOT NULL DEFAULT NOW(),

-- Mapeamento pedido iFood ↔ pedido interno (dedup/rastreio)
CREATE TABLE IF NOT EXISTS ifood_orders (
  id            BIGSERIAL PRIMARY KEY,
  restaurant_id INTEGER NOT NULL REFERENCES restaurantes(id) ON DELETE CASCADE,
  ifood_order_id VARCHAR(50) NOT NULL,          -- orderId do iFood
  pedido_id     INTEGER REFERENCES pedidos(id), -- pedido interno
  display_id    VARCHAR(20),
  status_ifood  VARCHAR(30),
  ultimo_evento VARCHAR(50),
  raw_payload   JSONB,
  criado_em     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  atualizado_em TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (restaurant_id, ifood_order_id)
);

-- Log/dedup de eventos (espelho de webhook_events)
CREATE TABLE IF NOT EXISTS ifood_events (
  id            BIGSERIAL PRIMARY KEY,
  event_id      VARCHAR(100) UNIQUE,            -- id do evento no polling
  event_code    VARCHAR(50),
  ifood_order_id VARCHAR(50),
  processed     BOOLEAN NOT NULL DEFAULT FALSE,
  error         TEXT,
  criado_em     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```
- `restaurantes` já tem `config JSONB` — alternativa leve: guardar settings no
  `config` (sem tabela nova). **Decidir na Fase 1** (tabela é mais tipada/auditável).

### 4.3 Mapeamento de status interno ↔ iFood
| Interno (atual) | iFood (ação/evento) |
|---|---|
| `pendente` (novo) | `PLACED` recebido → criar pedido interno |
| `preparando` (aceitar) | `POST /confirmation` → evento `CONFIRMED` |
| `pronto_entrega` | `POST /readyToPickup` |
| `em_transito` | `POST /dispatch` (modo own) → `DISPATCHED` |
| `entregue` | `POST /conclusion` (ou /delivery) → `DELIVERED`/`CONCLUDED` |
| `recusado`/`cancelado` | `POST /rejection` / `POST /cancellation` (com motivo) |
| — | `INTEGRATION_ERROR`/`INVALID` → alerta + pedido interno marcado |

Novo valor no enum `origem`: **`ifood`** (hoje: `delivery | salao | retirada`).

### 4.4 Integração com o que já existe (zero retrabalho)
- **KDS/painel:** `emitNovoPedido` / `emitPedidoAtualizado` (services/realtime.js)
  já levam o pedido para a fila — pedidos iFood aparecem automaticamente.
- **Timeline:** `pedido_timeline` ganha entradas com `usuario_tipo='ifood'`.
- **Validação de itens:** `validarItensPedido` deve **ignorar** validações de módulo
  (o item iFood não precisa existir como `produto_id` interno — vira item avulso).
- **Dedup/confiabilidade:** espelhar `webhook_events` (idempotência) + polling de
  backup (como `pollingRede.js`).
- **Push ao cliente:** o cliente iFood recebe notificações pelo app do iFood — a
  plataforma não envia push para clientes iFood (fora de escopo).

### 4.5 Configuração no Admin (restaurante)
Nova seção em `ConfigView.vue` (ou nova aba "Integrações"):
- Toggle **"Integrar com iFood"** (por tenant).
- Campos: `merchantId`, ambiente (sandbox/produção), modo de entrega.
- Botão **"Sincronizar cardápio agora"** + indicador da última sync.
- Aviso de estado (conectado/erro de token/último polling).

## 6. Decisões em aberto / riscos

| Item | Decisão/risco |
|---|---|
| Base URL e versões (2026) | `merchant-api` vs `pos-api`; campos depreciados do catálogo — **confirmar na homologação** |
| Aceite automático vs manual | SLA de ~5–7 min exige aceitar rápido; opção "aceitar automaticamente" por tenant (recomendada) |
| Itens avulsos | Pedido iFood pode ter itens que não existem no cardápio interno → sem validação de `produto_id` |
| Atualização de preço no iFood | Feita via catálogo; divergências com pedidos abertos são do iFood |
| Dedup e ordem de eventos | Eventos podem chegar fora de ordem — tratar por estado + `ifood_orders.status_ifood` |
| Credenciais | `clientId`/`clientSecret` globais no `stack.env`; **nunca** por tenant |
| Custos/contrato ISV | Verificar taxa ou licença de parceiro de software com o iFood (Fase 0) |
